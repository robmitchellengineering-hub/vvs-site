What Valiant proves

The AI says done. Valiant is the independent third party that makes done mean proven — with a human tether and a tamper-evident record of every action, and what approved it.

It is the one tool that closes the whole loop — verify → prove → block → coach → record → assure — for code an AI wrote.

Three ideas put Valiant on the other side of the table from a governance checklist:

The derivation is the asset, not the answer.

The machine-checkable steps an AI took — not just the result it printed — are the part you can reuse, teach and audit. An answer with no derivation is a rumour.

Who proofs the proofs?

A checker small enough to audit — the Lean kernel — and a check that has been proven to fail (mutation). The regress stops there, not at another model grading its own work.

An independent third party.

A signed verdict you re-run offline. Valiant's word is never the last word — the bytes are.

The fears, and what Valiant does about each

“The agent said done, and it wasn't.”

Valiant's gate is a verdict, not a claim — 0 holds · 1 broken · 2 could not check. Exit 0 is a contract, not a certificate: it means the checks you declared all passed — it is exactly as good as those checks, and it never lets an agent report “passing” unless the exit code is 0.

“Green, but nothing actually ran.”

Valiant proves the check can fail — it sabotages the code and requires the check to go red, then green when the sabotage is undone (mutation). A check that can't be made to fail is refused. Honest scope: this proves the check catches that seeded break — it does not prove the check catches every defect a future change could introduce.

“Nobody can tell me who approved this.”

Every action is recorded with its approval category — human-approved · policy-authorised (a safe read-only auto-approval) · pending (awaiting your tick) · rejected — plus restated and traceable, hash-chained. valiant audit prints the whole trail, and nothing reports “approved” unless the record says which kind.

“There's no off switch.”

The Stop hook halts the agent the moment it tries to finish red — in every environment where the hook is installed (pre-push, DSH and Claude Stop hooks). The control number (0/1/2) says whether it is under human authority. Honest limit: the hook is only as strong as the environment that runs it — a bypassed hook is a bypass, and the ledger records that it happened.

“The agent hides or mis-states what it did.”

The tamper-evident pack bundles every file's sha256 and a signed manifest, so a third party verifies offline: valiant pack --verify recomputes each hash and checks the signature against the public key shipped with the SDK. The agent's recorded actions and outcomes are compared to the actual diff — a claim that does not match the change it made is caught. It checks the account against the record, not the narration; it cannot read intent that was never written down.

“Approval is just rubber-stamping.”

Risk-tiered approval, recorded as a category not a blanket: genuinely read-only actions are policy-authorised (auto-approved by a conservative allowlist — no writes, no shell syntax, no secret paths); write / network / secret actions are pending until you tick them; a rejected action blocks. The human's attention goes where the blast radius is, and the ledger names which category every action got.

“The agent read the wrong thing into what I asked.”

Before it acts, the agent restates what it means (restated), closing the asked-vs-meant gap before the action, not after.

Conformance level (L1–L3)

A compliance team can check off the ladder by running valiant conformance — each level is computed from live evidence, not claimed:

levelwhat it provesthe statutory controls it satisfies
L1 — Verifiedthe gate runs, done is a 0/1/2 verdictNIST AI RMF Measure · EU AI Act Art 15
L2 — Proven+ the checks provably fail + every consequential action is human-ticked (safe read-only auto-approval excepted, and recorded as such)NIST Govern · EU AI Act Art 14
L3 — Assured+ a signed evidence bundle a third party verifies offlineEU AI Act Art 12 · ISO 42001 §7.5/§9

Every guard is also graded by evidence class — three classes that reinforce, not substitute for each other: empirical (mutation-tested: the check caught a real seeded break), exact (structurally proved by VVS's own kernel: the sabotage is unambiguous and the check is well-formed), kernel (Lean-checked: the claim that has a formal proof is type-checked in the pacland theorem tower). The kernel class applies only to the claims that are provable — the black-box behaviour of your check is observed, not proved.

Use it

curl -fsSL https://vvs.morpheus.nz/install.sh | sh   # installs the CLI, opens the control panel
# panel: 14-day trial → add a repo → toggle enforcement (no terminal after this)
valiant licence --file ./acme.licence                 # or CLI: your own licence, once per machine
valiant init                                          # adopt a repo (one valiant.json)

The agent gets the full operating manual automatically over MCP (no copy-paste); this is what it says:

1. VERDICT — before reporting done, call valiant_gate: 0 holds · 1 broken · 2 could-not-check.
2. COACHING LOOP — read the why + fix, re-run until 0. Do not bypass the block.
3. AUDIT — "who did what / who approved what" → valiant_audit.
4. COMPLIANCE — "how do we comply / what level" → valiant_report or valiant_conformance.
5. PROOF — before a final compile, run valiant prove (verify → mutate → control → audit → report → pack).
6. INTENT — restate what you mean in plain language; never copy the command.
7. TWO SPEEDS — iterate with gate daily; prove once before shipping.
